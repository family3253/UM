# PIVAS 智能用药助手 v0.8 Demo + 计划书 v1.1 设计

日期：2026-09-10
分支：pivas-https-demo

## 1. 目标

本轮不是增加单一按钮，而是把现有 Web Demo 与两份 v1.0 项目计划书重新对齐，使计划书中已经提出、且 Web 端可以真实演示的功能尽可能形成闭环，同时把用户后续新增需求正式纳入产品定义。

本轮交付包括：
- PIVAS Web Demo v0.8：完善一页式药品卡、语音搜索、当前药品语音问答、知识库管理演示、AI 建卡/审核演示、历史记录、说明书入口、API 设置和响应式布局。
- 主任汇报版计划书 v1.1。
- Codex/开发版计划书 v1.1。
- 更新并部署 GitHub `pivas-https-demo` 分支默认入口。

## 2. 已冻结的产品原则

1. 正常“扫码/OCR/搜索 → 药品卡”主链路不调用大模型。
2. 药品卡一屏速览优先，适应症不展示。
3. 药品顶部展示通用名、商品名、规格、厂家及产品图。
4. 调配、稳定性/贮存、输注/输液器、关键提醒为四个主模块。
5. 安全关键内容采用“红色 + 加粗”强调，不使用火焰等娱乐性图标。
6. 手机、Pad、桌面根据屏幕尺寸和横竖屏自适应字号与信息密度；Pad 默认更大，手机自动压缩。
7. AI 问答继承当前 Drug ID，不要求重复药名；无依据时明确提示无法确认。
8. AI 建卡只能生成 Draft，必须人工审核后发布。
9. 当前 PoC 不采集患者姓名、住院号、诊断，不接 HIS/PIVAS 患者数据。
10. Web Demo 是可演示原型，最终生产形态仍以 Android 平板原生 App 为目标。

## 3. v0.8 Web Demo 功能范围

### 3.1 首页与全局导航

首页保留“扫码/OCR识药”为主入口，同时增加可直接操作的语音搜索入口。首页展示本地知识库、AI 配置和语音能力状态，但不展示复杂系统指标。

### 3.2 语音搜索

新增首页麦克风按钮和独立语音搜索流程：
- 用户点击麦克风开始说药名/商品名/规格，如“维布妥昔单抗 50 毫克”。
- 浏览器支持 Web Speech API 时调用 `SpeechRecognition/webkitSpeechRecognition`。
- partial/final transcript 实时显示。
- final transcript 送入现有本地搜索/Drug Resolver。
- 唯一高置信匹配时直接打开对应药品卡；多个候选时显示候选列表；无匹配时保留文本并跳到手动搜索。
- 浏览器不支持语音识别时，按钮清晰降级并引导使用文字搜索，不影响其他功能。

语音搜索只做“输入方式替代”，不把语音识别结果绕过规格校验或低置信确认。

### 3.3 药品卡

6 个现有药品全部使用统一一页速览模板：
- 标题区：药名、商品名/英文名、规格、厂家、产品图。
- 四个核心信息块：调配、输注/输液器、稳定性/贮存、关键提醒。
- 关键数字、禁忌词和安全词按规则红色加粗。
- 无内容模块隐藏，不显示“无”。
- Pad/桌面横屏尽量一个视口完整展示；手机允许更紧凑排版，必要时轻微滚动。
- 保留“查看说明书”“询问 AI”。

### 3.4 当前药品语音问答

药品卡右侧 AI 抽屉保留文字问答并加强语音输入：
- 麦克风转写后自动填入问题。
- 当前药品上下文自动附带 Drug ID 和当前速览卡。
- 本地关键词可以回答卡片已有信息；若配置外部 API，再调用外部模型。
- 外部 AI 失败时自动降级为本地卡片回答。

### 3.5 知识库管理演示

Web Demo 增加真正可操作的知识库管理页面，而不只显示药品列表：
- 查看 6 个现有药品及状态。
- 搜索药品。
- 查看卡片版本、来源和更新时间字段。
- 提供“新增/更新药品”入口，进入 AI 建卡演示流程。

### 3.6 AI 建卡与审核演示

由于 Web Demo 无法完整复刻 Android 本地 PDF/OCR/Room，v0.8 实现前端闭环演示：
- 选择或拖入说明书 PDF/文本文件。
- 读取文件名、大小并显示处理状态。
- 若外部 AI 已配置，可按固定 JSON 结构生成 Draft；未配置时生成明确标注的 Demo Draft，不伪装成真实临床提取。
- 审核页逐字段可编辑。
- 必须勾选“已核对来源”后才能“审核并发布”。
- 发布只写浏览器 localStorage，标注为 Web Demo 本地草稿/演示，不替代正式知识库治理。

### 3.7 说明书入口

现有 6 张卡保留说明书入口。没有真实 PDF 绑定时，应明确显示“尚未绑定原始说明书”，而不是假装可打开。后续若本地资产绑定成功，再展示 PDF/来源定位。

### 3.8 历史记录

新增 localStorage 历史：
- 手动搜索/语音搜索成功记录。
- 扫码/OCR识别成功记录。
- AI 建卡 Draft/发布记录。
- API 测试状态可选记录。

历史仅记录 Drug ID、动作类型、时间和非敏感状态，不存患者信息。

### 3.9 API 设置

保留 Base URL、API Key、Model，并补充：
- Temperature（默认低值）。
- Timeout。
- 外部 AI 开关。
- 视觉兜底开关（默认关闭，仅作为演示设置）。
- 浏览器本地保存提醒。

Web Demo 必须继续提示：浏览器 localStorage 保存 Key 只适合 PoC；正式 APK 使用 Android Keystore/医院网关。

## 4. 响应式设计

采用三档视觉密度：
- 手机：约 320–620 px，较小字号、紧凑卡片、两列或单列按内容自适应。
- Pad：约 621–1100 px，默认较大字号，横屏两栏药品卡。
- 桌面/大 Pad：>1100 px，最大可读字号和更宽内容区。

字号使用 `clamp()` 与媒体查询结合，不使用单一固定 px。安全关键红色加粗样式在各设备保持一致。

## 5. 数据与安全边界

- 现有 6 个药品仍标注为演示/院内纸质卡转录，正式临床使用前需核对现行说明书和内部审核。
- 任何 AI 生成卡必须保持 Draft → Review → Publish 状态机。
- Web Demo 不引入患者信息。
- 不用 LLM 决定具体品规；规格冲突继续由确定性规则拦截。
- 语音识别结果只是搜索文本，不构成临床确认。

## 6. 两份计划书 v1.1 更新点

主任汇报版重点更新：
- 产品现状改为“已有可交互 Web PoC，持续向 Android 平板迁移”。
- 把“一页速览卡、产品图、红色加粗关键项、设备自适应字号”写成正式 UI 规范。
- 明确语音搜索已进入可演示功能，而非仅概念。
- 增加“Web PoC 能力 vs Android 正式能力”对照，避免把浏览器能力误写成生产能力。
- 调整里程碑状态：基础知识库、搜索、速览卡、Web 语音/AI 问答已有 PoC；原生 OCR/Room/Keystore 等仍属 Android 交付阶段。

Codex/开发版重点更新：
- 同步上述产品决策。
- 增加响应式 Web PoC 作为需求验证层。
- 明确首页语音搜索、药品页语音问答的状态路由和降级逻辑。
- 补充一页卡的 UI 约束、关键字段强调规则和产品图要求。
- 补充 Web Demo localStorage 与正式 Android Room/Keystore 的边界。
- 更新 M0–M9 里程碑与“已完成 PoC/待原生实现”状态。
- 加入 v0.8 验收清单。

## 7. 验收标准

v0.8 Demo 至少满足：
1. 6 张药品卡均使用同一速览结构、带产品图、关键项红色加粗。
2. 手机和 Pad 打开时字号与布局明显不同且不溢出。
3. 首页语音搜索在支持 Web Speech 的浏览器可将转写结果送入搜索；不支持时正常降级。
4. 药品页语音问答继承当前药品上下文。
5. 知识库、AI 建卡、审核、历史、API 设置都有可点击且可演示的页面流程。
6. 所有新增功能不引入患者数据。
7. 静态 JS 语法检查通过；现有搜索/识别主链路不因新增功能失效。
8. GitHub 分支更新后，默认 HTTPS Demo 入口指向 v0.8。
9. 两份 Word 计划书均升级为 v1.1，并与 v0.8 Demo 功能状态一致。

## 8. 测试策略

- JavaScript 静态语法检查。
- 本地搜索/匹配的基本回归测试。
- 语音 API feature detection 与不支持浏览器降级路径测试。
- localStorage 状态与历史记录测试。
- 不同 viewport 的布局检查：375×812、768×1024、1180×820、1366×768。

## 9. 非目标

本轮不声称完成：
- Android APK 原生 CameraX/ML Kit/Room/Keystore 的全部实现。
- 生产级离线 ASR。
- 医院 HIS/PIVAS 接口。
- 真实患者级处方审核。
- 未经核验说明书的临床级自动发布。
- 中国大陆生产级稳定托管方案。
